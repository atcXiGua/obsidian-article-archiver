# 竞品对比：obsidian-article-archiver vs 市面同类方案

> 更新：2026-11-07。本文回答一个问题：**「把网页文章归档到 Obsidian」这件事，市面上已有的方案和本 skill 到底差在哪？**

---

## 一、同类方案全景（4 类）

按「与本 skill 能力重合度」从高到低：

| 类型 | 代表项目 | 与本 skill 重合 | 核心差异 |
|---|---|---|---|
| ① 命令行归档器 | `article2md`、`feishu-docx` | 抓取 → MD → 本地图片 | 只到「落盘」，**无分类 / 双链 / 图谱** |
| ② 官方浏览器插件 | Obsidian Web Clipper | 保存网页 → MD | 浏览器手动操作，图片默认不下载，无中文登录墙 |
| ③ Skill 类（最接近） | `article-exporter`、`wechat-article-to-obsidian`、`article-to-obsidian-kb` | 都是「Agent Skill + Obsidian」形态 | 见第三节逐项对比 |
| ④ 知识图谱编排 | `claude-obsidian`、`connect-the-dots`、`ScholarSkill` | 双链 / MOC / 图谱 | 偏学术 / 研究场景，重语义抽取而非「原文完整留存」 |

**结论**：没有一个现成方案同时做到「完整原文留存 + 中文登录墙 + 自动分类 + 双链 + MOC + 图谱配色 + 跨机同步」这条完整链路。本 skill 的差异化不是单一功能，而是**把「归档」和「知识组织」串成一条自动化流水线**。

## 三、三个最接近者逐项对比

### 1. `article2md`（命令行归档器，最接近的「工具」）

- **相同**：都解决中文平台（公众号 / 知乎 / 小红书）登录墙 + 图片本地化 + 稳定命名。
- **差异**：它**止步于「抓下来存好」**，没有任何知识组织能力（无标签收敛、无双链、无 MOC、无图谱）。定位是「工具」，本 skill 定位是「流水线」。
- **它的优势**：`npm install -g` 一行安装、自带 MCP server、Playwright 复用浏览器会话抓取更鲁棒。

### 2. `article-exporter`（actionbook，最接近的「skill」）

- **相同**：都是「Agent Skill + 导出 Obsidian Markdown + 图片本地化 + 可选翻译」。
- **差异**：
  - 它**依赖外部 `actionbook` CLI + `obsidian-cli`**，本 skill 纯标准库零依赖；
  - 它默认会**「AI 重排」**（尤其 Twitter），本 skill 坚持**原文完整留存**；
  - 它**没有分类 / 双链 / MOC / 图谱 / 同步**，导出后是一个独立文件夹，不成图谱。

### 3. Obsidian Web Clipper（官方插件，最大的「生态」）

- **相同**：保存网页为本地 Markdown。
- **差异**：
  - 它是**浏览器手动操作**（点点鼠标），本 skill 是**对话触发**（贴链接即归档）；
  - 它**默认不下载图片**（链外链，离线会裂图），本 skill 图片本地化；
  - 它**不做任何知识组织**（分类 / 双链 / 图谱都靠你手动 + 装 Dataview）。

## 四、本 skill 的真实优势（3 点）

1. **「归档 + 组织」一体化**：别人都停在「抓下来存好」，本 skill 把「分类 → 分文件夹 → 双链 → MOC → 图谱配色」全自动。这是别人要额外靠 Dataview 插件 + 手动整理才能拼出来的后半段。
2. **中文登录墙 + 完整原文**的组合：`article2md` 会登录墙但定位是「工具」；`article-exporter` 是 skill 但中文平台是短板、且会重排。本 skill 两者兼得。
3. **同步闭环 + 配置化 + 工程化**：三脚本（use/sync/precommit）+ config.json + 幂等 + 47 测试，是绝大多数单文件 skill 没有的工程素养。

---

## 五、本 skill 的真实短板（3 点，需正视）

1. **生态与门槛**：`article2md` 一行 `npm install` 即用；本 skill 需「装 skill + 配 config.json + 跑 Python」，对非技术用户门槛偏高，且暂无 MCP 接口。
2. **抓取鲁棒性**：纯标准库 HTTP 抓取，面对**强反爬 / 需登录 / 动态渲染**页面比 Playwright 方案脆弱。这是「零依赖」的代价。
3. **星标 / 可信度**：0 star vs 竞品 5.4k、1.6k。差异化清晰，缺的是曝光。

---

## 六、结论

本 skill 的问题不是「有没有人对标」，而是**「差异化足够但缺最后一公里」**。市面同类都是「归档器」或「知识组织器」二选一，本 skill 是唯一把两者串成流水线、中文友好、且工程化的。真正的竞争点在：

1. 抓取鲁棒性要不要补（是否接受引入 Playwright 打破「零依赖」）；
2. 分发方式要不要给一个 `npx` / `MCP` 一键入口，降低门槛。
